## Goal and scope

Kestri learns useful personal context from ordinary owner dialogue, recalls it across paraphrases, and updates it when the owner changes their mind. Explicit remember/correct/forget controls remain available. First delivery covers direct personal facts, goals, preferences, decisions, temporary state, candidate inference, hybrid recall, bounded history search, and revocation. It does not infer diagnoses/personality or authorize tasks/actions from memory. Success means useful correct recall, not merely successful vector generation.

## Trust and user controls

Auto extraction requires an owner-level opt-in; first upgrade defaults off and does not backfill old history. Capture an activation message watermark. Only new direct authorized owner messages may substantiate automatic facts. Assistant messages help resolve references but are never personal-fact evidence. Forwarded messages, external replies, quoted sources, tools, and generated summaries cannot authorize or substantiate facts. Persist provenance at ingestion: direction alone is insufficient. Quoted/hypothetical speech inside a direct message must still be excluded by extraction.

`/remember` has highest retention intent. Natural-language corrections and forgetting use an independent control resolver: unique explicit target commits; ambiguous targets produce a bounded candidate list and require selection. Do not expose arbitrary model-selected IDs as authorized targets. Ordinary automatic additions may show one concise change notice; repeated reinforcement is silent. Notices must use the current epoch and durable outbox, not send inside extraction transactions.

Planned interfaces: `/memory`, `/memory pending`, `/memory changes`, `/memory auto on|off`, and a separate memory-use setting. Disabling extraction cancels queued work and blocks in-flight commit, but does not disable using existing memories. Disabling use stops memory/history injection. Enabling again sets a fresh activation watermark unless explicit backfill is requested. Credentials are never eligible; sensitive personal information requires explicit retention intent. Define sensitive categories conservatively and evaluate their classifier; no claim of perfect detection.

## Logical data model

Keep PostgreSQL source records authoritative. Core profile is a query over active stable memories, not a second generated copy of facts. Extend `memories` with `category` (`preference/background/goal/decision/current_state`), `origin` (`explicit_command/auto_direct/auto_inferred`), `revision`, `fact_key`, `valid_from`, `review_after`, and `last_source_message_id`. Preserve identity, scope/task, supersedes, expiry, provenance, and existing active/superseded/forgotten/expired/quarantined statuses; add candidate status. Content is an atomic statement of at most 600 characters for automatic extraction; retain the existing 1200-character explicit command contract. `fact_key` is a merge hint, not a uniqueness constraint or proof of equivalence. Owner-defined task scope requires a known association; do not infer a task UUID from ordinary prose. Project labels can be metadata without granting task scope.

Add `memory_sources(memory_id,message_id,quote,start,end)` with FK to local `messages.id`; positions use Python Unicode code-point offsets. Record owner and source eligibility through joins. Keep Telegram message IDs separately. Add `memory_jobs` (type, owner, source IDs, source watermark, captured revision/epoch/settings generation, status, lease, attempts, next attempt, safe error category, unique idempotency key, maintenance run ID), `memory_events` (operation, IDs, revisions, reason category, job ID, timestamp), and `memory_embeddings` (memory ID, content revision/hash, embedding space, vector, timestamp). Events do not duplicate forgotten content indefinitely.

Owner state adds `auto_memory_enabled`, `memory_use_enabled`, `memory_revision`, `automatic_history_floor`, activation watermark, and settings generation. Existing `memory_epoch` remains the revocation boundary. Candidate inference is never supplied as an established fact. Capacity is explicit: proposed limit 1000 active memories and 100 candidates per owner, with no silent eviction of explicit memories. On capacity exhaustion, defer new additions and expose maintenance status; replacements/reinforcement remain possible. These replace the current 64-active-memory limit only when this feature ships.

## Extraction input and output

Message acceptance and job registration commit together; extraction must not depend on successful reply delivery. Defer background work until foreground capacity is available; owner facts can still be learned after a failed reply. Process source IDs in chronological order. Each batch contains at most 8 new owner messages, at most 12 adjacent context messages total, and at most 24000 UTF-8 bytes of source text. Apply activation/floor eligibility to all supplied history, including assistant context. Oversized single messages remain archived but are marked extraction-ineligible with a safe category; do not silently truncate a claim. Read at most 20 relevant existing memories under a separate bounded input allowance. Full request admission includes schema and instructions.

The model returns a strict Pydantic schema, at most 8 operations. Each operation contains action (`create/reinforce/replace/candidate`), optional target ID and expected revision, category, content, fact key, scope, basis (`direct_statement/inference`), source IDs and verbatim quotes with offsets, valid time, expiry, and review time. No arbitrary SQL, tools, deletion, task authorization, or executable instructions. A direct statement may become active; an inference remains candidate. A model's confidence number is not a calibrated probability. Candidate approval needs an owner action; repeating model guesses does not promote them.

Before committing, verify schema/size, exact source quote and offsets, batch membership, owner, eligibility, secret filters, target state/scope/revision, chronology, and temporal constraints. Quotation checks prove provenance existence, not semantic correctness. The model proposes; application validation and a transaction decide. A successful job with no operations still advances its processing cursor.

## Consolidation and temporal semantics

Create for a new explicit fact; reinforce genuinely equivalent facts by adding independent source references; replace an explicitly changed attribute by inserting a new row and superseding its predecessor. Coexisting preferences stay separate. Ambiguous contradictions remain candidate and do not override established facts. Never replace an explicit memory with an inference. Older input cannot override a newer statement (`last_source_message_id` plus version checks). Do not assume the model-generated fact key makes a replacement safe.

Explicit temporal bounds become expiry. Vague current-state statements get a proposed 30-day review interval, not fabricated certainty about an expiry date. After review time, omit from ordinary current-state injection; historical recall may describe it with its date. Stable facts do not automatically expire. Expiry is enforced at access and commit boundaries. Time interpretation uses owner timezone and UTC storage; relative expressions refer to source-message time.

## Retrieval and context assembly

On each model request, obtain a consistent eligible memory snapshot. Select at most 6 direct stable communication preferences, at most 2000 characters; select at most 8 related facts, with total memory injection at most 6000 characters. No zero-match recent-memory padding. Explicit retention does not imply universal relevance.

Construct query text from current request and at most 4 recent dialogue messages, maximum 4000 characters. Initial delivery uses this bounded text directly, without a separate query-rewrite call. Filter by owner, active status, scope, task state, expiry, review time, and content version before exact search. Retrieve up to 20 lexical and 20 dense candidates, merge with Reciprocal Rank Fusion (`k=60`), then one bounded model-selection call returns only eligible candidate IDs and can select none. Define a Chinese lexical tokenizer/bigram implementation and lock its version; PostgreSQL default language configurations are not assumed to provide adequate Chinese segmentation. Dense threshold belongs to a particular model/encoding-space version and is calibrated on evaluations, not assumed universal.

Before injection, recheck status, revisions, settings generation, and epoch. On revision change repeat local selection once; on revocation abort stale work. Limit the selection call to 12000 UTF-8 bytes, no retries on foreground failure, and charge it to the foreground budget. A timeout, unknown usage, or provider failure falls back to bounded lexical retrieval, with no fabricated semantic score. Inject records as attributed untrusted data, never permissions. Selected memories stay out of graph messages, though generated answers can repeat them.

## Embedding and storage contract

Initial provider: Beijing DashScope `text-embedding-v4`, 1024-dimensional float output. The [implemented adapter](../reference/embedding.md) uses the official workspace-compatible endpoint, at most 10 texts/request, bounded reads, and validates all indices/dimensions/finite nonzero vectors and usage. Document the exact encoding recipe; if switching to native query/document modes later, treat the recipe as a new space. `embedding_space` identifies provider, region, model, dimensions, recipe, and application version. Model aliases can drift; monitor probe behavior and retain index-generation metadata, without claiming immutable vendor weights.

Write facts first and enqueue embeddings atomically. Generate vectors outside SQL transactions; commit only if source memory is still active and content revision/hash matches. Unique keys prevent duplicate index publication; orphan/stale computation may cost money but cannot reactivate facts. Input revisions without vectors remain lexically searchable. Initially use pgvector exact cosine search; add HNSW only after size/latency/recall measurement. Server must have the extension installed before `CREATE EXTENSION`; no automatic change to a live volume from the connection feature.

Vectors live in the existing database, in a separate `vector(1024)` table joined to current facts. Queries must constrain embedding space and content revision. Different models cannot share a comparison space even at equal dimensions. Changing provider/model/recipe builds a separate generation and switches only after validation; never partially mix spaces. Plan explicit migration/upsert SQL and deletion tests before activating storage. No vector DDL has shipped yet.

## History retrieval

Planned tools: `search_history(query,before?,after?,limit<=5)` and `read_history_segment(segment_id)`. Owner is supplied by the application, never model arguments. Index eligible dialogue segments of at most 12 messages and 8000 characters, split on turn boundaries; retain message IDs, roles, dates, and source hashes. Skip or separately handle oversized single messages without silent truncation. Tool schema/result and retrieval request sizes are bounded by existing tool/admission rules.

Use time filters and hybrid recall; exclude purged, quarantined, or floor-ineligible content. Search returns snippets and source handles; read rechecks eligibility. Owner decisions require owner evidence; assistant proposals remain attributed proposals. Initial index starts at opt-in. Historical backfill is a separate authorized operator action and must honor deletion/floor rules. `/history` remains explicit owner-only archive viewing outside model context. History chunks and embeddings are not personal facts.

## Jobs, concurrency, accounting, and failures

One extraction commit lane per owner. `queued → running → succeeded`, or `running → retry_wait → running`, ending in failed/cancelled. Claim using row locks and a time-limited lease; proposed lease 120 seconds, provider timeout 20 seconds, maximum 3 total attempts with 5/30-second retry delays. Recovery reclaims expired leases; never hold a DB transaction across HTTP. Idempotency key uses owner, job type, source range/hash, and extractor version. Use captured settings generation/revision/epoch and target revisions as compare-and-swap checks. Version conflicts rebuild input; at most 3 conflict rebuilds, then defer to a fresh job without losing source progress. Commit changes, events, cursor, and job success in one transaction.

A dedicated maintenance run kind is required because current usage rows reference runs. Extraction/index calls reserve costs against owner monthly total and a separate maintenance cap before HTTP. Proposed caps: 1 CNY per maintenance job and 10 CNY per month; foreground selection remains under its run cap. Define one ledger currency/conversion policy before implementation: the current ledger is micro-USD, while this provider bills CNY; do not silently add amounts in different currencies. Keep configured conversion rate/version and original currency estimate, and conservatively reserve unknown usage. Free quota does not bypass local budgets. No background maintenance ledger exists in this connection release; smoke is one deliberately invoked paid request with reported usage, outside DB ledger.

Retry only bounded transient failures; authentication/schema failures require operator action. Foreground response does not wait for extraction. Log counts, versions, durations, safe errors and usage, not full prompts/keys/vectors. Expose job status and index-generation progress. Proposed extraction SLO: eligible messages processed within 60 seconds while service is healthy, idle capacity and budget are available; this is an acceptance target, not a current guarantee.

## Revocation and lifecycle

Add/reinforce increments memory revision without resetting conversation. Replace/correct/forget/expiry retains conservative epoch increment and head reset. Existing model/tool/finish gates continue rejecting stale epochs. Natural-language control commits are serialized with extraction and invalidate in-flight proposals.

For the first version, forgetting also advances the owner's automatic history floor to the last currently archived message ID. All automatic extraction, history search/read, summaries supplied to extraction, and index rebuilds exclude messages at/below that floor. All jobs recheck floor at commit. Other unrelated active memories remain eligible; broad loss of old automatic history recall is explained in the receipt. The explicit `/history` view stays available. New direct statements after the cutoff may create new memories. Do not rely on a semantic tombstone classifier as a guarantee against resurrection.

Source deletion invalidates affected automatic facts, history segments, embeddings, cached selection and graph state in a defined transaction; explicit retained facts can persist according to existing explicit-retention policy, but removed source excerpts must not persist in source/event tables. Forgotten/superseded content and raw history follow documented retention, not immediate global physical erasure. Evidence/files and vendor copies remain separately governed. Extend backup schema/version before shipping; keep jobs/settings/activation/floors/events in a consistent snapshot, but omit rebuildable vector indexes. Restore disables extraction/use, quarantines facts, clears checkpoints and derived indexes, and cancels maintenance work. Re-enable requires explicit owner action; historical extraction must not run automatically after restore.

## Acceptance and rollout

Deterministic tests cover provenance exclusion, exact quotation checks, candidate isolation, scoped access, atomic acceptance/job registration, repeated claim/restart idempotency, stale update/disable/forget races, vector failures and stale publication, restore quarantine, cleanup dependency handling, and budget reservations. All ownership/revocation cases must pass. Separate actual provider proof from mock and PostgreSQL integration evidence.

Maintain at least 100 Chinese labeled evaluation cases with paraphrases, pronouns, temporary emotions, hypotheses, quotations, conflicting preferences, historical decisions and no-relevant-memory queries. Proposed gates: active-fact precision ≥95%, direct-fact extraction recall ≥85%, semantic Recall@8 ≥90%, and no-relevant-memory false injection ≤5%; document corpus, labels, denominators and scorer versions. Never infer general memory quality from one embedding smoke comparison.

Delivery order: (1) standalone embedding connection and docs, implemented; (2) opt-in/provenance/jobs/auto extraction and semantic fact storage with offline + disposable-DB checks; (3) model-path hybrid recall and concurrency/lifecycle integration; (4) history tools and evaluations; (5) isolated live Telegram and restart/forget/restore acceptance. Implement with `MemoryExtractor`, `MemoryRepository`, `MemoryRetriever`, `HistoryRetriever`, and a maintenance worker. The explicit-only product remains active until later increments meet their gates.

Implemented extraction, fact indexing and history indexing share USD maintenance caps of 0.15/job and 1.50/month. DeepSeek extraction and versioned CNY-to-USD embedding accounting are implemented. Publication uses one fresh message per job and at most 3 total attempts, including conflicts; exhausted jobs fail visibly without infinite requeue. `/memory changes` is read-only; automatic change notices and bounded literal-target natural-language correction resolution are implemented; the independent memory-use switch is implemented. See [progress](../development/memory-v2-progress.md) for exact deviations and deployment/evaluation boundaries.

Migration 6 implements semantic storage/indexing and the bounded hybrid model path; [runtime reference](../reference/semantic-memory.md) owns actual behavior. It adds a separate semantic opt-in and use switch, fingerprints symmetric L2 encoding, uses 0.5 CNY/million with a versioned fixed 0.15 USD/CNY estimate, performs provider selection at most once per run, and retries additive version changes locally. These are explicit implementation choices; fact candidate calibration, history tools and isolated synthetic live acceptance are recorded; full extraction/selection quality and historical JSON calibration remain outstanding.

The [history runtime reference](../reference/history-retrieval.md) documents implemented bounded lexical/hybrid search, progressive semantic caching and persistent background indexing, available with both auto/use enabled, with context reset on auto changes. The [local deployment](../how-to/deploy-memory-v2.md) is complete with auto/semantic off; implementation and synthetic regression acceptance are complete; see the [completion record](../development/memory-v2-completion.md) for limitations.
