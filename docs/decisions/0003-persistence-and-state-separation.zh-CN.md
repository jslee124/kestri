# ADR-0003：使用 PostgreSQL，分离对话、记忆、任务与执行状态

[English](0003-persistence-and-state-separation.md) · [文档](../README.zh-CN.md)

- 状态：已接受
- 决策日期：2026-09-30
- 更新日期：2026-10-01
- 实现：M1 已实现消息、checkpoint、执行、发送、用量与证据；任务和记忆表结构及保留期执行后续实现

## 背景

一个 Telegram 聊天需要支持对话、持续工作和个人记忆，而不是一个无限增长的模型请求。重启、上下文压缩、纠正、忘记和发送恢复，需要不同的持久记录。

项目是单用户本地应用，但长期个人使用要求超越内存演示的持久化。存储需要易于理解，并支持已有框架适配器。

## 决策

使用一个本地 PostgreSQL 实例保存持久应用记录和 LangGraph 状态。完整研究材料和生成文件保存在专用工作区，数据库记录引用与来源。

维护独立逻辑类别：原始消息归档、图检查点、个人记忆、任务约定、执行和发送、证据元数据。这是语义隔离，M1 研究表结构和适配器已实现；任务与记忆生命周期表结构仍待确定。

使用主对话线程与独立后台执行上下文。通过消息关联检索相关任务证据，不合并完整后台历史。

LangGraph 提供线程级 checkpointer 和跨线程 store，两者都有 PostgreSQL 适配器。见[持久化指南](https://docs.langchain.com/oss/python/langgraph/persistence)、[检查点参考](https://reference.langchain.com/python/langgraph/checkpoints)和 [PostgresStore 参考](https://reference.langchain.com/python/langgraph.store.postgres/base/PostgresStore)。业务任务状态和原始归档仍由 Kestri 负责。

个人记忆初期采用结构化与关键词检索，不选择独立向量数据库或 embedding 服务。记忆以显式写入为主，推断偏好需要同意。压缩和记忆写入属于独立操作。

## 考虑过的备选方案

| 备选方案 | 取舍 |
| --- | --- |
| 内存状态 | 适合简单实验，但重启后丢失持久状态 |
| SQLite | 对小型本地应用合理；选择 PostgreSQL 是为了已有检查点、store 适配器和已确认的持久化学习目标 |
| 只用检查点保存历史 | 压缩和裁剪可能移除原始消息，执行状态也不定义任务授权或记忆生命周期 |
| 所有工作共用一个永久线程 | 后台轨迹增加上下文，使任务和证据关联更困难 |
| 优先使用向量记忆 | 语义检索价值尚未证明，就引入 embedding、检索与删除复杂度 |
| 多个专用数据库 | 增加运维和一致性边界，第一版没有实际需求 |

## 影响

PostgreSQL 增加本地服务、备份与迁移责任。选择它本身不意味着产品已达到生产质量，也不保证并发正确。

独立记录让任务控制、来源、纠正和恢复更易于推理，但需要一致标识符和有意识的生命周期协调。围绕外部 Telegram 调用使用数据库事务，也不能直接保证恰好发送一次。

忘记与保留策略必须处理摘要、检查点、成果和备份中的副本。旧历史被裁剪后，当前执行状态必须仍可使用。恢复旧数据时，重新执行前必须处理已删除任务和已忘记记忆。

详细生命周期规则见[安全与数据](../design/security-and-data.zh-CN.md)，默认参数和流程见[架构](../design/architecture.zh-CN.md)，验收标准见[需求](../design/requirements.zh-CN.md)。

## 复审条件

安装负担、实测并发、规模或离线需求与选定部署冲突时重新评估。实际记忆使用暴露局限后再加入语义检索。改变存储或恢复旧数据前，审查归档、保留和删除语义。
