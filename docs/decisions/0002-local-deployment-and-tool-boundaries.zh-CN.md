# ADR-0002：使用 Docker Compose 本地部署与受控工具

[English](0002-local-deployment-and-tool-boundaries.md) · [文档](../README.zh-CN.md)

- 状态：已接受
- 决策日期：2026-09-30
- 更新日期：2026-10-01
- 实现：尚未开始；隔离与部署未验证

## 背景

用户希望通过 Telegram 访问本地通用个人 agent，同时避免意外破坏现有文件。初始流程需要公开网页获取、任务管理、记忆和工作区成果，不需要任意代码或直接电脑控制。

## 决策

使用 Docker Compose 运行本地应用和 PostgreSQL。Telegram 采用私聊、长轮询与用户 ID 白名单。长轮询避免为当前部署配置公网入站 webhook。Telegram 在 [Bots FAQ](https://core.telegram.org/bots/faq#how-do-i-get-updates) 中说明了轮询与 webhook。

第一版只暴露受控应用工具。应用使用专用工作区，不广泛访问本机目录。不暴露任意 shell 或代码执行、已连接账号修改或 Docker daemon socket。

服务凭据和个人数据库位于模型可见工作区之外。应用策略检查每次模型工具请求。受控搜索和提取按明确的 URL、输出和时间策略访问公开互联网，文件操作限制于任务范围。

确实需要代码执行时，引入独立短生命周期沙箱，只提供任务文件，不提供服务凭据或个人状态。准确的创建机制和沙箱技术配置需要后续设计。具体策略见[安全与数据](../design/security-and-data.zh-CN.md)。

## 考虑过的备选方案

| 备选方案 | 取舍 |
| --- | --- |
| 仅本机原生部署 | 开发方便，但缺少已选部署中的文件和进程边界 |
| 整个应用与任意脚本同处一个容器 | 让脚本执行可接触应用凭据和持久数据 |
| 广泛可写挂载 home 目录 | 访问方便，但给现有文件带来不必要风险 |
| 立即使用专用 VM | 更强隔离可能有价值，但在流程需要任意执行前增加操作系统维护 |
| 云端托管 agent | 改变本地运行目标，也不能消除已连接账号权限带来的风险 |
| Telegram webhook | 需要可入站访问的接口，第一版本地部署不需要 |

## 影响

初始部署依赖 Docker 可用以及本机保持唤醒和联网。电脑停机会影响调度工作，通过有边界的补跑策略处理，而不承诺始终在线。

工作区仍是真实持久用户数据。可写绑定挂载可以修改本机文件，Docker 隔离不会自动保护挂载原件。[官方绑定挂载文档](https://docs.docker.com/engine/storage/bind-mounts/)说明了这一行为。

受控工具具有应用进程权限，需要认真验证，并不等同于独立的不可信代码沙箱。应用配置中的凭据通过设计不暴露给模型，但无法因此抵御应用本身被攻破。

设计减少暴露能力，同时保留可复用的信息流程，不构成绝对安全保证。恢复、边界检查、资源限制与安装后部署行为都需要验证。

## 复审条件

加入脚本、插件、浏览器会话或电脑控制工具时重新评估隔离。持续在线或新增交互入口成为实际需求时重新评估部署。扩大本机或账号访问需要明确权限并更新验收标准。
