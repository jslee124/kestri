## 环境与边界

2026-10-02，功能分支工作区的当前 Python 代码连接独立 PostgreSQL 17、pgvector 0.8.7 和临时工作区。通过 Chrome 中已登录的 Telegram 向现有主人专用机器人发送合成消息。确认没有排队/执行任务、待发送消息或活跃持续任务后，暂时暂停原应用轮询；结束后恢复，健康检查通过。生产数据库没有迁移，测试消息没有进入其归档。截图和本地备份不提交 Git。原机器人仍使用之前的镜像，这是隔离验收，不是常驻部署。

[脱敏证据](evidence/memory-v2-live.json)记录基线提交、实际执行 Python/SQL 的源码 hash、固定阈值、隔离数据库数量、用量以及实际 checkpoint 工具名。不包含凭据、主人 ID、机器人 ID、私人归档、端点或原始向量。执行的是提交前的修改工作区，源码 hash 与基线 SHA 分别标明。

## 已验证流程

自然聊天中的合成清淡饮食偏好自动生成 `auto_direct` 有效事实，没有使用 `/remember`；事实及历史向量均写入。`/new` 后以不同措辞查询，仍返回该偏好，账本记录真实的 `memory_query` 与 `memory_select`。关闭学习并重启 Python 后，已有事实仍可召回。`/forget` 删除对应事实向量并重置上下文，随后查询回答“不知道”。

新建上下文后回查合成项目决定，持久工具消息确认执行了两次 `search_history` 和一次 `read_history_segment`。回答引用完整主人消息，区分助手确认，给出来源 ID 和有界覆盖说明。这证明该流程可用，不证明通用历史召回质量。

停止源应用后生成 schema 7 备份，通过 CLI 恢复到新的空数据库/工作区。三条活跃项目事实变为隔离状态，已忘记的事实仍保持忘记，三个记忆开关全部关闭，五个历史作业被取消，两张向量表均为空。启动恢复实例后发送恢复说明，随后的项目查询没有使用导入记忆。旧执行和发送没有重放。

## 失败与实现响应

第一条饮食来源的引用验证失败两次，其中第二次是隔离环境中的人工诊断重试。随后向提取器提供完整消息的精确 Unicode 引用锚点，仍检查合格的新主人来源、逐字引用/位置与当前版本。新偏好成功提取。项目来源首次失败，人工重试一次后成功。证据保留这些失败，没有计为首次成功。

最终代码仅保存白名单静态失败原因，区分未知 ID、来源不合格、引用、跨度、位置及敏感内容。模型生成的 ID/引用/跨度/位置错误可在原有三次上限及 5/30 秒间隔内重新生成；同意开关、来源资格、敏感内容及目标策略拒绝仍立即终止。受控测试验证引用错误重试耗尽和不发布部分事实；没有做真实重试耗尽验收。这些改动改善不透明失败，不证明提取可靠性门槛达标。

源账本总额为 10,530 微美元，恢复导入该历史账本后，最终查询新增 360 微美元：此次真实流程新增费用估算合计 **USD 0.010890**，不把导入用量重复计费。此值不含独立 embedding 语料评测；配置估算不是服务商发票。
